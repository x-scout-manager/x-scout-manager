# Xスカウト支援ツール 要件定義書

## 1. 文書概要

本書は、Xスカウト支援ツールの開発にあたり、機能要件、非機能要件、運用条件、契約前提、技術構成、プロジェクト進行方針を整理することを目的とする。

本案件は、初期開発費を抑える代わりに成果連動報酬を含む全体報酬設計を前提とした案件であり、以下の条件を前提とする。

- 初期開発費：20万円（税別）
- 支払条件：契約時5万円、検収後15万円
- 月額保守費：1万円（税別）
- 成果報酬：本件システム経由で成約した成果対象者の対象売上の10%
- 成果報酬は保守契約終了後も継続
- 成果報告は2か月ごと

---

## 2. プロジェクト概要

### 2.1 プロジェクト名

Xスカウト支援ツール開発プロジェクト

### 2.2 背景

X上で特定タグを起点としたスカウト業務を効率化したいというニーズがある。

現状は、候補抽出、プロフィール確認、送信可否判断、送信履歴管理などに手作業が多く、運用負荷が高い。また、同一アカウントへの重複接触、除外対象者への誤送信、送信履歴の管理漏れなどのリスクがある。

### 2.3 目的

本プロジェクトの目的は以下のとおりとする。

- 特定タグを起点に候補アカウントを抽出する
- プロフィール文による除外判定を行う
- 候補一覧を管理画面で確認できるようにする
- DM送信作業を支援する
- 既送信アカウントへの重複接触を防止する
- 最低限の送信履歴と除外管理を持たせる
- 成果報酬の根拠となる証跡を保存する
- 運用を小さく始め、必要に応じて段階的に拡張できるようにする

## 3. 開発方針

### 3.1 基本方針

本システムは、スモールスタートを前提とし、初期フェーズでは必要最小限の機能に絞って構築する。

初期フェーズでは、候補抽出、プロフィール除外、候補一覧、候補詳細、送信支援、送信履歴、簡易ステータス管理、成果証跡管理を中心に実装する。

高度な分析機能、返信管理、複数担当者管理、詳細なマーケティング支援機能などは本フェーズの対象外とし、必要に応じて追加開発として扱う。

### 3.2 DM送信に関する基本方針

本フェーズでは、候補一覧に対する確認操作なしの自動一括DM送信は行わない。

本システムは、候補抽出、既送確認、テンプレート表示、送信対象選択、送信キュー管理、個別DM送信、送信履歴保存を行う「チェック選択式・送信キュー型の個別DM送信支援機能」として構築する。

管理者は、候補一覧から送信対象者をチェック選択し、選択された候補者を送信キューに追加できるものとする。

送信キューでは、候補者ごとにプロフィール、除外判定結果、既送信履歴、DM本文を確認したうえで、管理者が1件ずつ送信操作を行う。

本機能は、管理者の確認操作を伴う個別送信支援機能であり、候補一覧に対して確認なしで連続送信する自動一括送信機能ではない。

ただし、短時間に多数のDMを送信する運用は、X側の制限、レート制限、アカウント制限、スパム判定等のリスクがある。そのため、必要に応じて送信間隔、送信上限、警告表示等を設ける。

X API上でDM送信が利用できない場合、または利用リスクが高い場合は、管理画面上でテンプレート本文をコピーし、X上で手動送信した後、送信済みとして記録する運用に切り替える。

### 3.3 外部サービス利用に関する基本方針

X API、Firebase、その他第三者サービスの仕様変更、利用制限、障害、審査不通過、アカウント制限、凍結等により、本システムの一部または全部が利用できなくなる可能性がある。

これら第三者サービスに起因する問題は、本システムおよび乙の保証範囲外とする。

## 6. 想定利用フロー

### 6.1 候補抽出フロー

1. 管理者が管理画面にログインする
2. 管理者が対象タグを設定する
3. 管理者が候補抽出を実行する
4. Cloud Functions が X API を利用してタグ検索を行う
5. 投稿主アカウントを抽出する
6. 既存候補、既送信、除外対象との重複確認を行う
7. プロフィール文に対して除外キーワード判定を実施する
8. 候補または除外として Firestore に保存する
9. 管理画面の候補一覧に表示する

### 6.2 DM送信支援フロー

1. 管理者が候補一覧を確認する
2. 管理者が検索条件やステータス等により候補者を絞り込む
3. 管理者が送信対象候補者にチェックを付ける
4. 選択された候補者を送信キューに追加する
5. 送信キュー画面で、1件ずつ候補者の詳細を確認する
6. 管理者がDMテンプレートを選択する
7. システムが既送信履歴、除外状態、送信可否を確認する
8. 管理者がDM本文を確認する
9. 管理者が候補者ごとに「DM送信」操作を行う
10. Cloud Functions が X API を利用してDM送信を実行する
11. 送信成功時に送信履歴を保存する
12. 候補ステータスを送信済みに更新する
13. 次の送信キュー候補へ進む

X API上でDM送信が利用できない場合、または利用リスクが高い場合は、管理画面上でテンプレート本文をコピーし、X上で手動送信した後、送信済みとして記録する運用に切り替える。

## 7. 機能要件

### 7.1 認証機能

- Firebase Authenticationを利用してログインできること
- 未ログイン状態では管理画面にアクセスできないこと
- 初期フェーズでは管理者1名から小規模利用を想定すること
- 必要最低限のアクセス制御を行うこと

### 7.2 タグ設定機能

- 対象タグを登録できること
- 登録済みタグを確認できること
- 初期フェーズではシンプルなタグ設定とすること
- 複雑な条件分岐やタグごとの詳細設定は対象外とすること

### 7.3 候補抽出機能

- 指定タグで投稿検索を実行できること
- 投稿主アカウントを抽出できること
- 抽出済み候補との重複を確認できること
- 既送信アカウントを再候補化しないこと
- 除外対象アカウントを候補から除外できること
- 候補一覧を取得・表示できること

### 7.4 プロフィール除外機能

除外対象キーワード例：

- 事務所所属
- 事務所運営
- agency
- manager
- 所属中

要件：

- 除外キーワードを設定できること
- プロフィール文に除外キーワードが含まれる場合、除外扱いにできること
- 除外されたアカウントを保持できること

### 7.5 DM送信支援機能

- 候補一覧から送信対象者をチェック選択できること
- 選択された候補者を送信キューに追加できること
- 送信キューでは候補者ごとにプロフィール、除外判定結果、既送信履歴、DM本文を確認できること
- 管理者が候補者ごとに1件ずつDM送信操作を行えること
- 送信前に既送信履歴を確認できること
- 既送信対象には送信できない、または警告表示できること
- 除外対象には送信できない、または警告表示できること
- 送信成功時に送信履歴を保存できること
- 送信成功時に候補ステータスを送信済みに更新できること
- 候補一覧に対して確認なしで連続送信する自動一括送信は行わないこと

## 15. 実装前補強事項

本章は、2026-05-11時点のドキュメント精査結果をもとに、実装前に固定する追加方針を整理する。

### 15.1 X API検証を最優先に行う

X API連携は、本システムの成立可否に直結するため、UI実装より前に以下を確認する。

- Developer App の承認状態
- OAuth 2.0 PKCE によるユーザーアクセストークン取得可否
- DM送信に必要な `dm.write` / `dm.read` スコープの利用可否
- 投稿検索APIの利用可否
- 対象プランにおける検索件数、期間、レート制限
- DM送信APIの実送信またはテスト送信可否

X APIのDM送信が利用できない場合、初期MVPではAPI送信を無効化し、テンプレートコピーと手動送信済み登録を中心機能として提供する。

### 15.2 投稿検索条件の明確化

指定タグ検索では、以下の条件を設定項目またはシステム設定として保持する。

- 対象タグ
- 検索対象期間
- 1回あたり取得件数
- 最大取得ページ数
- 除外する投稿条件
- 同一ユーザーを再検出した場合の更新方針

X APIのRecent Searchは直近期間の検索を前提とするため、過去投稿を広範囲に検索する要望は追加検討対象とする。

### 15.3 DM送信方式の優先順位

初期MVPでは、以下の順で実装・検証する。

1. テンプレート本文表示
2. 本文コピー
3. 手動送信済み登録
4. 送信履歴保存
5. X API疎通確認
6. X APIによる個別DM送信

X APIによるDM送信は、疎通確認、権限確認、運用リスク確認が完了した場合のみ有効化する。

### 15.4 二重送信防止

DM送信処理では、二重クリック、複数タブ操作、Cloud Functionsの並列実行による重複送信を防止する。

Cloud Functions側では、送信前にFirestore transactionを使い、対象候補またはキュー明細を `sending` 状態へ更新する。すでに `sending`、`sent`、`excluded` の場合は送信処理を実行しない。

送信成功時は `sent`、送信失敗時は `failed` とし、必要に応じて再試行可能な状態へ戻す。

### 15.5 成果証跡の保存

成果報酬の根拠として、最低限以下の証跡を保存する。

- 候補ID
- XユーザーID
- Xユーザー名
- 抽出元タグ
- 初回抽出日時
- 初回接触日時
- 送信履歴ID
- 送信方法 `api` / `manual`
- 送信本文スナップショット
- 成果登録日時
- 対象売上
- 成果報酬率
- 成果報酬額
- 登録者UID
- 補足メモ

成果報酬額は、登録時点の対象売上と報酬率から算出し、スナップショットとして保存する。

### 15.6 管理者権限

初期MVPでは管理者1名からの利用を想定するが、権限判定方式は実装前に固定する。

推奨方針は以下とする。

- Firebase Authenticationでログインする
- `users/{uid}` に `role = admin` を保持する
- Cloud Functions側で `role = admin` を確認する
- Firestore Security Rulesでも未ログインユーザーを拒否する
- 重要な作成・更新処理はCloud Functions経由に限定する

Custom Claimsを利用する場合は、設定・更新運用が必要になるため追加検討対象とする。

### 15.7 除外状態の責務

除外状態は以下の責務で管理する。

- `excluded_accounts`: 永続的な除外対象リスト
- `candidates.status`: 一覧表示・操作制御用の現在状態
- `candidates.isExcluded`: 表示高速化用のスナップショット

正本は `excluded_accounts` とし、候補更新時に `candidates` 側へ反映する。
