# 032 候補一覧のページングと遅延描画

## 現状の動作

- Flutter Webの候補一覧はFirestore `candidates` を件数制限なしでリアルタイム購読している。
- `SingleChildScrollView` 内の `DataTable` に全候補を渡し、画面外を含む全行を一括生成している。
- 候補数が増えるほどモデル保持、レイアウト、描画の負荷が増え、iOS SafariでWebContentプロセスが終了する可能性がある。

## 期待する動作

- Firestoreから候補を一定件数単位で取得する。
- 次ページ・前ページ操作で必要な候補だけを取得する。
- 一覧は表示範囲を中心に遅延構築し、候補総数に比例して描画メモリが増えない。
- ページを移動しても、送信対象として選択した候補IDを維持する。

## 操作フロー

1. 管理者が候補一覧を開く。
2. 最新順の候補が1ページ分表示される。
3. 「次へ」を押すと次ページを取得する。
4. 「前へ」を押すと前ページへ戻る。
5. 複数ページで候補を選択し、送信キューへ追加する。
6. 候補抽出後は先頭ページを再読み込みする。

## 技術方針

- `view / vm / usecase / data / model` の責務分離を維持する。
- Repositoryにページ取得とFirestoreカーソル管理を閉じる。
- `status asc, updatedAt desc` の既存複合インデックスを利用する。
- 初期ページサイズは50件とする。
- UIは `ListView.builder` 等の遅延構築Widgetを利用し、親の縦方向 `SingleChildScrollView` に全件を載せない。
- ページ履歴はViewModelで管理し、選択済み候補IDはページとは独立して保持する。
- 候補抽出・解除・再掃除後は先頭ページを再取得する。

## 完了条件

- 初回表示で50件を表示し、次ページ判定用の1件だけを追加で先読みする。
- 次ページと前ページへ移動できる。
- 最終ページでは次ページ操作が無効になる。
- ページ移動後も選択済み候補IDが維持される。
- 候補抽出・解除・再掃除後に先頭ページが更新される。
- 候補一覧が遅延構築される。
- 既存の候補選択・送信キュー作成が動作する。
- Flutterテストと `flutter analyze` が通る。

## レビュー指摘

- PWA表示時に候補一覧で「問題が繰り返し起きました」となり、最近は重くなっている。
- 候補件数増加に比例する全件取得・全件描画を解消する。

## 備考

- UIだけのページ分割では全件取得を解消できないため、Firestoreクエリ自体をページングする。
- iOS PWA固有のレンダラー・Service Worker検証はタスク034で扱う。
- 1ページ50件と次ページ判定用1件を取得するカーソル方式へ変更した。
- 候補表示を `SliverList` に変更し、画面外の候補行を初期構築しないことをWidgetテストで確認した。
- ViewModelを画面State所有へ変更し、画面再構築時に古い購読が残る可能性を解消した。
- 全Flutterテスト、`flutter analyze`、`flutter build web --release` が通過した。
